## 2. Phase 2 — cause analysis, tied to the code

1. **Scale.** `project.godot` renders 320×180 with 16px tiles; `tools/artgen/__init__.py`
   sets `CHAR_H = 16`. A character is 1/11 of the screen height. HGSS/BW-class
   overworld sprites are ~24–32px tall with four-direction walk cycles, a
   recognisable head/hair/clothing silhouette and a shadow. Here there is no
   room for folds, expression or a distinct outline.
2. **Tile craft.** `tools/artgen/terrain.py` explicitly says "detail is placed,
   not scattered" and uses 2 macro blobs at `macro_alpha=0.35` plus `grains=0.012`.
   The intent is good, but at 320×180 the result is a clean flat base with a few
   isolated pixels — visually identical to the random noise the brief forbids.
   Four variants of the same macro-structure also make the field read as wallpaper.
3. **No lighting model.** `scripts/world/Region.gd::set_time_of_day()` applies one
   `CanvasModulate` colour (dusk = `0.80,0.62,0.55`) to the whole world. There is
   no per-location palette, no directional light, no ambient occlusion and no
   contact shadow. `art/characters/*_idle.png` have internal shading but no
   ground shadow, so figures float.
4. **Geometric props.** Trees, rocks and sheep are drawn from circles, triangles
   and ovals in `tools/artgen/props.py`. No hand-authored silhouette.
5. **Only two maps.** `data/regions/` contains `elah.json` and `bethlehem.json`.
   Samuel's anointing and Saul's court are dialogue-only. The valley and the
   shepherd field are two areas of the *same* map.
6. **UI with no material language.** `scripts/ui/Hud.gd` and
   `scripts/story/DialogueBox.gd` hardcode near-black `Color(0.03…0.10)` plates.
   Nothing ties the UI to the world palette, and the 9px CJK font
   (`fonts/game.ttf`, 826 codepoints — gate clean) has no size hierarchy.

## 3. Phase 3 — three prototypes (real alternatives, not filters)

The reference was **`tests/frames/baseline_06_flock.png`** — the existing
shepherd-field screenshot — with the HUD band removed and upscaled to 1280×720
(`prototypes/00_reference_shepherd.png`). Three **separate** concept images were
generated from it, each with a different brief; the user chose one candidate for
each direction (`prototypes/A|B|C_*_source.png`). They differ in composition,
architecture, vegetation, lighting and clothing — see
`prototypes/01_sources_contact.png`.

| | A — Vibrant Classic RPG | B — Rich Cinematic Pixel Art | C — Biblical Storybook RPG |
|---|---|---|---|
| World | sunny meadow, pale pebble path, chunky layered trees, blue sky strip | golden-hour hillside, long cast shadows, terraced walls, hazy distance, near-silhouette foreground | dry-stone terraces, worn limestone path, gnarled olive trees, clay-roofed hamlet, Levantine ochre |
| Light | flat bright, upper-left | single low warm source, cool violet shadows | warm morning, gentle cool shade |
| Clothing | simple rust tunic / blue robe | rim-lit expressive figures | striped wool tunic, headcloth, woven sash, linen mantle |
| UI | deep indigo + gold double border | near-black + amber rule | parchment + brown ink + ochre frame |

`tools/art_reset/build_prototypes.py` then: centre-crops to 16:9, reduces to the
game's **native 320×180**, applies a per-direction tone curve, reduces to a
**controlled 64-colour palette with no dithering**, removes isolated single-pixel
confetti by editing palette indices, and draws a direction-specific HUD and
dialogue panel at the **same position, same size, same Chinese strings** using the
shipped `fonts/game.ttf` (1-bit glyphs, no anti-aliasing) and the shipped 32×32
portrait. All four panels therefore share one cast and one composition.

**Pixel-accuracy verification / its limit.** The concept sources are 1376–2816px
paintings. They were verified as *still* 320×180 pixel composites: controlled
palettes (52 / 66 / 67 colours), no dithering, no isolated noise, crisp 1-bit
type. They were **NOT** verified for animation consistency, atlas tiling, tile
seams or walk cycles — because they are not sprite sheets. Section 6 treats that
as a hard limitation, not a success.

Specific failings, not generic praise:

- **A** is the most readable and has the widest tonal range, but that range comes
  largely from a **bright blue sky strip that breaks the orthographic top-down
  map**. It is a generic fantasy meadow: no Levantine architecture, no biblical
  dress, saturation 0.668 pushes it toward candy. Its trees are still soft
  painted masses, not pixel clusters. Its saturation 0.632 is the highest of
  the four and pushes it toward candy.
- **B** has the best real depth — long shadows, atmospheric haze, a clear focal
  path — but it is **too dark and too desaturated for a morning shepherd field**
  (sat 0.403), its near-silhouette foreground occludes walkable ground, and the
  characters are small dark dots. Its mood belongs to the confrontation in the
  valley, not to the flock.
- **C** is the most detailed (edge 0.317) and the most coherent, but its detail is
  a weakness: **busy stone/grass texture with the weakest large-scale value
  hierarchy (18.7)**, so the player and the sheep are hard to find. Its parchment
  UI is the only one that belongs to the world, yet it is bright enough to
  compete with the ground (UI luma 195.5).
- **Current** is not merely dark: its world is a single value plane with two
  black UI holes, geometric props and 16px figures with no readable clothing.

### Selection

**Direction C — Biblical Storybook RPG** is selected. Not because it is brightest
(A is the most saturated, C the highest mean luma) and not because it is most
detailed (its edge density is the weakness): because it is the only direction
that gives Bethlehem, the shepherd fields, Saul's court and the valley a
**shared, historically appropriate identity** while keeping the UI in the same
material world.

> **Superseded 2026-11-10:** this was the assistant's selection. After reviewing
> the attached painted concept, the user explicitly chose Direction B's outcome
> with the existing animation preserved. C is retained for comparison. See
> §12.6–§12.7; the selection text above is history, not the active target.

Three mandatory corrections are borrowed from the other two directions — this
is a combination, not a fourth style:

1. **B's value hierarchy / single-light logic**, not B's palette. Implemented as
   the `C+` refinement (`comparison/selected_refinement_native.png`): atmospheric
   darkening at the far edge, a brighter focal middle ground, a darker near edge,
   mild contrast S-curve, re-snapped to the same palette. Value spread improves
   **18.7 → 21.2** with no new detail.
2. **A's clean, high-contrast silhouettes and consistent 1px outline** for the
   player and interactables — to be applied by hand-authored sprites (section 6).
3. **Background texture suppression** around the player, so readability comes
   from colour strategy rather than from flattening every background element.

## 6. Phase 6 — pixel-art craftsmanship and environment depth: the hard limit

**The existing code-based PNG generation process cannot produce the required
craftsmanship on its own, and AI concept art is not a remedy.** Evidence: the
new storybook atlas in `storybook_tiles_4x.png` has a better palette but the
*identical* tile shapes — the same flat rectangles, the same sparse 1px tufts,
the same wall pattern. The real before/after frame shows blob trees and boxy
16px figures unchanged. Downsampling a 2816px painting to 320×180 produces a
review image, not an animation-consistent, tileable, walkable sprite sheet.

What professional-level quality actually requires:

1. **Hand-authored character sprites.** 16×24 or 16×32, four-direction walk
   cycles plus idle/turn frames for the 12 named actors: distinct silhouettes
   (staff, sling, headcloth, mantle, armour), 1px outline, 3–4 value clothing
   folds, readable faces, and a ground contact shadow. Consistent pixel size,
   no stretched sprites.
2. **Hand-authored location tile sets.** Bethlehem village (wall/roof/shadow
   faces, doorways, street), shepherd fields (dry-stone terraces, olive grove,
   limestone path, wildflowers in deliberate clusters), Saul's court (a distinct
   interior with readable volume), valley (ridge, strata, dust, scale). Each
   tile 16×16 with 3–4 value steps and organic transitions, no random 1px noise.
3. **Layered composition.** Explicit foreground (grass/rock silhouettes),
   middle ground (playable space, characters), background (hills, hamlet, haze);
   large natural landmarks; clear cast shadows; a focal point that does not hurt
   navigation.
4. **Environmental animation** at the same pixel scale: grass sway, water,
   dust, torch/lamp light, sheep idle — with verified frame consistency.
5. **Original art production.** A pixel artist drawing the sheets, or a coherent
   CC0 pack re-authored to this palette (the current `assets/LICENSES.md` rejects
   the packs that do not fit). AI image generation is useful for **art-direction
   concept art only**, which is exactly how it was used here; it must not be
   claimed as a shipped asset source.

Programmatic generation stays useful for controlled patterns, palettes, atlas
packing and regression gates — which is how this project already uses it — but
not as the only art-production method.

## 10. Limitations and next checkpoints

* No human playtest, no perceptual audio check, no native-speaker Chinese pass,
  no real-device tactile/rotation/safe-area pass (carried over from
  `docs/BROWSER-VALIDATION.md`).
* The three prototypes are concept composites. **No animation frames, no tile
  slicing, no seam testing, no in-engine render of the prototypes.** They prove

### 12.10 Why the first live screenshot was still classic — and the runtime fix

The user opened the live URL and sent a screenshot with the bright classic
green field, blue water and classic HUD, asking **"why still same"**. The
deployment was current: the live `index.service.worker.js` carried cache stamp
`d6f067cba19ab770f50b0800d6b16f2fcc131b1c`, so this was not a stale Pages
build. The real cause was a scope mistake in the assistant's work: all B v3
assets and lighting were present, but `Main.apply_art_theme()` was only called
by `tests/visual.gd` for frames 16/17. The shipped game's `_ready()` never
called it, so a normal Web boot still used classic terrain, props, HUD and
dialogue. The user was invited to "feel" B but was shown classic.

**Fix on this working branch.** `Main.gd` now has
`const WEB_PREVIEW_THEME := "cinematic"` and `_preview_art_theme()` returns it
only when `OS.has_feature("web")`. `_on_region_ready()` applies the theme after
every cold boot and every region swap, so the live Pages preview shows B at the
first frame and after travel. Desktop, headless suites and the Xvfb visual
harness still return `"classic"`, so the 17 committed frame baselines remain
valid. This is a **runtime theme call**, not a default asset replacement:
`art/tiles/terrain.png`, `art/props/`, `art/characters/` and every classic file
are untouched, and setting the constant back to `"classic"` restores the old
look exactly. Gameplay, collision, animation, quests and save format are not
changed.

**Still partial.** The B theme covers Region terrain, crafted props/actors,
HUD and dialogue. Dedicated setpiece screens (`GoliathFight`, `SlingPractice`,
`StoneChoice`) and the journal/menu/transition surfaces do not yet have B
skins, so this is not a whole-game art replacement or a parity claim. Human
playtest is still required. Because this is a PWA, a browser that already
cached an older build may need one hard refresh / clear-site-data before the
new sha-stamped service worker takes over; the deployed worker's cache name
changes with the commit sha. No PR, no merge to `main`, no release.
